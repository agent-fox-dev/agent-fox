# Requirements Document

## Introduction

This document specifies the abort post-mortem feature for the `agent-fox code`
command. When an orchestrator run exits non-successfully, the system writes a
self-contained JSON diagnostic file to `.agent-fox/audit/` so that the abort
cause can be understood without manual investigation of audit logs or database
tables.

## Glossary

- **Post-mortem**: A JSON file written after a non-successful orchestrator run
  containing diagnostic information about why the run was aborted.
- **Run status**: The terminal status of an orchestrator run, represented by
  the `RunStatus` enum (COMPLETED, STALLED, BLOCK_LIMIT, COST_LIMIT,
  SESSION_LIMIT, INTERRUPTED).
- **Trigger status**: A run status that causes a post-mortem to be generated.
  Includes STALLED, BLOCK_LIMIT, COST_LIMIT, and SESSION_LIMIT.
- **run_id**: A unique identifier for each orchestrator run, formatted as
  `{YYYYMMDD}_{HHMMSS}_{hex}`. Generated by `generate_run_id()`.
- **Blocked task**: A task node whose status is "blocked", meaning it cannot
  proceed due to upstream failures, review findings, or cascade effects.
- **ExecutionState**: The in-memory dataclass that holds all run state
  including node statuses, session history, costs, and timestamps.
- **Audit directory**: The `.agent-fox/audit/` directory where agent traces,
  audit events, and post-mortem files are stored.

## Requirements

### Requirement 1: Post-mortem trigger conditions

**User Story:** As a developer, I want a diagnostic file to be automatically
generated when a run fails, so that I can understand the failure without
manually inspecting audit logs.

#### Acceptance Criteria

1. [126-REQ-1.1] WHEN `run_code()` returns an `ExecutionState` with
   `run_status` equal to STALLED, BLOCK_LIMIT, COST_LIMIT, or SESSION_LIMIT,
   THE system SHALL generate a post-mortem JSON file AND return the file path
   to the caller via `state.postmortem_path`.

2. [126-REQ-1.2] WHEN `run_code()` returns an `ExecutionState` with
   `run_status` equal to COMPLETED, THE system SHALL NOT generate a
   post-mortem file.

3. [126-REQ-1.3] WHEN `run_code()` returns an `InterruptedResult` (status
   INTERRUPTED), THE system SHALL NOT generate a post-mortem file.

#### Edge Cases

1. [126-REQ-1.E1] IF post-mortem generation raises an exception, THEN THE
   system SHALL log a warning with the exception details and continue
   returning the `ExecutionState` without a post-mortem path.

2. [126-REQ-1.E2] IF the `ExecutionState` has an empty `run_id` (e.g., from
   `_stalled_result()`), THEN THE system SHALL generate a fallback run_id
   using the current timestamp and write the post-mortem using that id.

### Requirement 2: File output

**User Story:** As a developer, I want the post-mortem file to be easy to
find and correlate with other audit artifacts from the same run.

#### Acceptance Criteria

1. [126-REQ-2.1] WHEN a post-mortem is generated, THE system SHALL write it
   to `.agent-fox/audit/postmortem_{run_id}.json` where `{run_id}` is the
   orchestrator's run identifier.

2. [126-REQ-2.2] THE post-mortem file SHALL contain valid JSON that can be
   parsed by any compliant JSON parser.

3. [126-REQ-2.3] WHEN the audit directory does not exist, THE system SHALL
   create it before writing the post-mortem file.

#### Edge Cases

1. [126-REQ-2.E1] IF writing the post-mortem file to disk fails (e.g.,
   permission error, disk full), THEN THE system SHALL log a warning and
   continue without the file.

### Requirement 3: Schema structure

**User Story:** As a tool author, I want a versioned, stable schema so that
I can build tooling that parses post-mortem files reliably across versions.

#### Acceptance Criteria

1. [126-REQ-3.1] THE post-mortem JSON SHALL include a `schema_version` field
   set to the integer `1`.

2. [126-REQ-3.2] THE post-mortem JSON SHALL include the following top-level
   keys: `schema_version`, `run_id`, `run_status`, `started_at`,
   `completed_at`, `task_summary`, `cost_summary`, `blocked_tasks`,
   `session_history`.

3. [126-REQ-3.3] THE `task_summary` object SHALL include integer fields:
   `total`, `completed`, `pending`, `blocked`, `failed`, `in_progress`.

4. [126-REQ-3.4] THE `cost_summary` object SHALL include: `total_cost_usd`
   (float), `total_input_tokens` (integer), `total_output_tokens` (integer),
   `total_sessions` (integer).

5. [126-REQ-3.5] THE `blocked_tasks` field SHALL be a JSON array (empty
   array `[]` when no tasks are blocked).

6. [126-REQ-3.6] THE `session_history` field SHALL be a JSON array (empty
   array `[]` when no sessions were recorded).

### Requirement 4: Blocked task reporting

**User Story:** As a developer, I want to see exactly which tasks are blocked
and why, so I can address the root cause directly.

#### Acceptance Criteria

1. [126-REQ-4.1] WHEN the `ExecutionState` contains blocked tasks, THE
   system SHALL include one entry per blocked task in the `blocked_tasks`
   array, each with `node_id` (string) and `reason` (string) fields.

2. [126-REQ-4.2] THE `blocked_tasks` array SHALL be sorted by `node_id` in
   ascending lexicographic order.

#### Edge Cases

1. [126-REQ-4.E1] IF a task is in the `node_states` dict with status
   "blocked" but has no entry in `blocked_reasons`, THEN THE system SHALL
   include it in `blocked_tasks` with `reason` set to `"unknown"`.

### Requirement 5: Session history and cost reporting

**User Story:** As a developer, I want to see the full timeline of session
attempts so I can identify patterns (repeated failures, cost hotspots,
transport errors).

#### Acceptance Criteria

1. [126-REQ-5.1] THE system SHALL include every `SessionRecord` from
   `state.session_history` in the `session_history` array, each with fields:
   `node_id`, `attempt`, `status`, `archetype`, `model`, `duration_ms`,
   `cost`, `error_message`, `timestamp`, `is_transport_error`,
   `is_budget_exhausted`, `is_non_retryable`.

2. [126-REQ-5.2] THE `cost_summary` SHALL reflect the aggregate values from
   `state.total_cost`, `state.total_input_tokens`,
   `state.total_output_tokens`, and `state.total_sessions`.

#### Edge Cases

1. [126-REQ-5.E1] IF `session_history` is empty (e.g., run stalled before
   any session started), THEN THE system SHALL include an empty
   `session_history` array and zero values in `cost_summary`.

### Requirement 6: CLI integration

**User Story:** As a developer using the CLI, I want to see the post-mortem
file path in the output so I know where to look.

#### Acceptance Criteria

1. [126-REQ-6.1] WHEN a post-mortem file is written, THE `_print_summary()`
   function in `cli/code.py` SHALL print the file path to stdout.

2. [126-REQ-6.2] WHEN no post-mortem file is written (successful run or
   interrupted), THE `_print_summary()` function SHALL NOT print a
   post-mortem path line.

### Requirement 7: run_id on ExecutionState

**User Story:** As an internal consumer, I want the run_id to be accessible
on the ExecutionState so I can correlate the post-mortem with other audit
artifacts.

#### Acceptance Criteria

1. [126-REQ-7.1] THE `ExecutionState` dataclass SHALL include a `run_id`
   field (string, default empty string).

2. [126-REQ-7.2] WHEN the Orchestrator initializes a run, THE system SHALL
   set `state.run_id` to the generated run identifier before returning the
   state.
